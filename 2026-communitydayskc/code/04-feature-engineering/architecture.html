🧠 Feature Engineering: The Most Important Layer

💡 Core Principle: Feature engineering is where the domain knowledge lives — and that knowledge belongs in Java. Business data access, merchant risk tables, geo risk databases, and business rules are already wired up in Java. The ML model should only see clean, numeric features — not raw domain objects.

🔧 Feature Engineering Categories

⏰ Temporal Features

Time-based risk signals extracted from transaction timestamp:

  • Hour of Day (0-23) — fraud peaks at 2-4 AM
  • Day of Week (0-6) — weekend patterns differ
  • Is Overnight (bool) — overnight = higher risk
  • Is Weekend (bool) — weekend fraud profile distinct

🏷️ Categorical Encoding

Domain knowledge → normalized risk scores:

  • Merchant Category → 0.0-1.0 risk
  • Country Code (ISO-2) → geo risk
  • Channel (ONLINE, ATM, etc) → risk
  • Domain Lookup Tables — pre-computed risk scores

📊 Velocity Features

Detects abnormal transaction bursts:

  • Txn 1h — count in last 1 hour
  • Txn 24h — count in last 24 hours
  • Txn 30d — count in last 30 days
  • Requires VelocityStore — Redis or in-memory cache

📈 Derived Ratios

Complex features from amount + history:

  • Amount Normalized — log1p(amount)
  • Avg Amount 7d — rolling average
  • Amount to Avg Ratio — detects abnormal spends
  • Requires Transaction History — time-series cache

🔄 Feature Engineering Pipeline

Raw Transaction

accountId, amount, timestamp, merchant, country, channel

→

Temporal

Extract hour, day, overnight flag, weekend flag

→

Categorical

📊 Raw Data vs. ML Features

❌ Raw Transaction (Not for ML)

⚠️ Problem: Contains non-numeric data, requires domain knowledge to interpret, not normalized.

📋 Feature Engineering Best Practices

🔢 Always Normalize Amount

Use log1p(amount) to reduce skew from large outliers. Fraud amounts follow long-tail distribution — ML models handle log-space better.

🏠 Keep Domain Knowledge Separate

Risk lookup tables (merchant, geo, channel) belong in Java config/database, not hardcoded in models. Easy to update business rules without retraining.

📚 Preserve Raw Values in Metadata

Alongside normalized features, keep original values for debugging, audit trails, and explainability. "Why was this flagged?" — check metadata.

⏱️ Use Velocity with Caution

Velocity features require state management (Redis, in-memory cache). Cold-start problem for new accounts. Consider time-decay functions for old transactions.

🎯 Feature Independence

Avoid highly correlated features (e.g., amount and log-amount together). More features ≠ better. Domain knowledge guides feature selection.

🔄 Track Feature Definitions

Document every feature: source, transformation, normalization. Version your feature definitions. Retraining with different features invalidates old models.

💡 Key Insights from the Talk

🏗️ Enterprise ML Success = 80% Feature Engineering

The model is only 20%. The other 80% is getting clean, relevant features. Spend time on domain understanding, business rule translation, and data quality.

☕ Feature Engineering Belongs in Java

Because: (1) Business rules are in Java, (2) Database connections are in Java, (3) Merchant/geo tables are Java, (4) Team owns the code. Don't separate concerns artificially.

🔗 The ML Model is Dumb

The model only knows how to find patterns. It doesn't know "2 AM is risky" or "Nigeria is high-risk" — YOU tell it via features. Garbage in = garbage out.

🎯 Feature Engineering is Iterative

Start simple. Measure model performance. Add features strategically. Backtest against historical fraud. Don't over-engineer. Simpler = faster + easier to explain.

📊 Explainability Starts with Features

If fraud alerts are hard to explain to Risk Ops, check your features. Keep metadata. Include "why" alongside predictions: "CRYPTO + NG + 2AM + high velocity = HIGH RISK".

💻 Java Feature Engineering Code

// FeatureEngineer: Core feature extraction logic public TransactionFeatures extract(Transaction txn) { // Temporal features int hourOfDay = txn.timestamp().getHour(); int dayOfWeek = txn.timestamp().getDayOfWeek().getValue(); // Categorical encoding via lookup tables double merchantRisk = merchantRiskTable.get(txn.merchantCategory()); double geoRisk = geoRiskTable.get(txn.location()); // Velocity features via cache query int count1h = velocityStore.getCount("1h", txn.accountId()); int count30d = velocityStore.getCount("30d", txn.accountId()); // Derived ratios double amountNormalized = Math.log1p(txn.amount()); double avgAmount = historyStore.getAvgAmount7d(txn.accountId()); double amountRatio = txn.amount() / Math.max(1, avgAmount); // Return both features + metadata return new TransactionFeatures( amountNormalized, hourOfDay, dayOfWeek, merchantRisk, geoRisk, count1h, count30d, amountRatio, Metadata.of(txn) // Keep raw values ); }

🏷️ Why Keep Metadata?

🔍 Debugging

When prediction is wrong, metadata shows you exactly what inputs led to the decision.

📋 Compliance & Audit

Regulators require "why was this flagged". Metadata provides full audit trail from raw data to features to decision.

🎯 Explainability

Risk Ops wants to understand: "Is it the amount, the time, the merchant, or the geography?" Metadata answers that.

📊 Feature Validation

Monitor feature distributions over time. Detect data drift. Compare raw vs engineered values to catch bugs.

🔄 Retraining

When retraining, you need to replay historical transactions through the same feature pipeline. Metadata helps rebuild context.

🚀 Feature Evolution

Store metadata, then try new features. A/B test old vs new features on same raw data.
