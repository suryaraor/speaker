The Compliance Team's Dream — 100% Java, Zero External Dependencies

Weka · RandomForest in Java Air-gapped · Fully auditable

The compliance team had a list of requirements that made the Python-based approaches complicated: no external binaries in production containers, every line of model logic must be auditable in the Java codebase, and the system must work in an air-gapped environment where Python simply wasn't available.

The answer: Weka. A full machine learning library, written in Java, that's been running in financial systems since the late 90s. Train a RandomForest at startup, entirely in Java, and it lives right there in JVM memory — fully auditable by any Java developer on the team.

}

Chapter 3 · example 02-onnx-in-jvm

The Passport Trick — Train in Python, Run in Java

ONNX Runtime · In-JVM Inference Sub-millisecond · No Python at runtime

A senior engineer on the team had seen ONNX used in a previous job. The idea: train your model in Python however you like — scikit-learn, XGBoost, PyTorch — then export it to a universal binary format called ONNX. Java loads the binary and runs inference directly inside the JVM using ONNX Runtime.

Think of ONNX as a passport. The model is trained in the Python world, stamped with an ONNX passport, and then it travels freely into the Java world. No visa required. No Python process needed at runtime.

OnnxFraudDetector.java — inference entirely in the JVM 
public FraudPrediction predict(TransactionFeatures features) throws OrtException {
    long start = System.nanoTime();
    float[][] inputMatrix = new float[][]{ features.toArray() };

    try (OnnxTensor tensor = OnnxTensor.createTensor(env, inputMatrix);
         OrtSession.Result result = session.run(Map.of("float_input", tensor))) {

        float[][] probs = (float[][]) result.get("probabilities").get().getValue();
        float fraudProb = probs[0][1];

        long elapsedNs = System.nanoTime() - start;
        // Typically: 150–200 microseconds. Compare to 10–50ms for HTTP.
        return new FraudPrediction(fraudProb, fraudProb > 0.85f, riskLevel(fraudProb), elapsedNs);
    }
}

The Quick Win — Call Python Over HTTP

REST · WebClient · Fallback Python FastAPI + sklearn

The data science team already had a RandomForest model for fraud detection sitting in a Jupyter notebook. The fastest path to production: wrap it in a FastAPI service and call it from Spring Boot.

Java handles what Java is already great at — feature extraction from domain objects, business rules, SLA enforcement — and hands off a clean numeric vector to Python for inference.

"The key insight: don't let Java become dumb glue. Feature engineering — the transformation of raw transaction data into ML-ready numbers — stays in Java, where the domain knowledge already lives."
FraudDetectionService.java — 500ms SLA with graceful fallback 
private static final Duration SLA_TIMEOUT    = Duration.ofMillis(500);
private static final FraudScore SAFE_FALLBACK = new FraudScore(
    0.0, false, "fallback-v0", "LOW", Map.of()
);

public FraudScore evaluate(Transaction tx) {
    TransactionFeatures features = featureEngineer.extract(tx);
    return callMlService(features)
        .onErrorReturn(SAFE_FALLBACK)   // Python down? Don't block the payment.
        .block();
}

private Mono<FraudScore> callMlService(TransactionFeatures features) {
    return mlWebClient.post()
        .uri("/predict/fraud")
        .bodyValue(features)
        .retrieve()
        .bodyToMono(FraudScore.class)
        .timeout(SLA_TIMEOUT);  // Fail fast. Fraud check isn't worth a 30s hang.
}
Works For
Fastest path to production. Data science team owns the model independently. Any Python framework works.
The Catch
Network hop on every transaction. Python service is another thing to deploy, monitor, and page on at 2am.

The team shipped this in a sprint. Fraud dropped 40% in week one. Then Black Friday arrived and the Python service started timing out under load. They needed something faster.

TransactionConsumer.java — one annotation, the whole pipeline starts 
@KafkaListener(topics = "transactions", groupId = "fraud-detection")
public void consume(@Payload String payload) {
    TransactionEvent event = objectMapper.readValue(payload, TransactionEvent.class);

    TransactionFeatures features = featureEngineer.extract(event);
    FraudScore score = fraudScoringService.score(features);

    if (score.isFraud()) {
        fraudAlertService.raise(event, score);  // publishes to "fraud-alerts" topic
    }
}

// FraudScoringService tries ONNX first (fast path), falls back to REST
public FraudScore score(TransactionFeatures features) {
    if (onnxDetector.isAvailable()) {
        return onnxDetector.predict(features);   // sub-ms, in-JVM
    }
    return restFallback.score(features);        // REST if .onnx not loaded
}

Chapter 6 · the decision guide

So Which Pattern Do You Actually Use?

Decision Matrix When to Use What

These aren't five competing patterns. They're five different answers to five different questions your team will face. Here's how to think about picking one:

Pattern Pick this when… Latency Ops overhead
03 · REST Data science team owns the model lifecycle independently. Model changes often. You need OpenAPI docs and monitoring for free. 10–50ms High — another service to run
02 · ONNX Latency matters. You want sub-ms inference. Model changes occasionally. You're OK with Python at train time, not runtime. <1ms Low — one .onnx file
01 · Native (Weka) Air-gapped or compliance-restricted environment. No Python anywhere. Team is Java-only. Tabular data, not deep learning. <1ms Zero — lives in the JAR
05 · Pipeline You need async, event-driven ML scoring at scale. Kafka already in your stack. Downstream systems need the fraud signal. <5ms e2e Medium — Kafka + compose
"The realistic production journey: start with 03 (REST) to get something working fast. Migrate the hot path to 02 (ONNX) for low latency. Use 01 (Native) for compliance-restricted subsystems. Wire it all with 05 (Pipeline) for event-driven scale. And from day one, use 04 (Spring AI) to explain every score to your stakeholders."

The realistic production answer for most teams: start with 03 (REST) to get something working fast and let data science iterate. Migrate the hot path to 02 (ONNX) once you understand the load. Use 01 (Native) for compliance-sensitive sub-systems. Wire it all together with 05 (Pipeline) when you're ready for event-driven scale.

And from day one, use 04 (Spring AI) to make every ML score explainable — because a score your stakeholders can't understand is a score they won't trust.

The Moral of the Story

Heartland Bank didn't replace their Java stack with Python. They didn't build a separate "ML platform." They taught Java to think by meeting ML where it makes sense — at the feature layer, at the inference layer, at the integration layer — and letting each language do what it's best at.

Python is the best language for training models. Java is the best language for running the business. These are not mutually exclusive. The patterns in this talk are the bridge.
