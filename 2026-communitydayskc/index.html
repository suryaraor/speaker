Architecture

Three Patterns to Bridge Java and ML

🌐

Pattern 1: Model as a Service

ML model runs in Python (Flask / FastAPI). Java calls it over HTTP REST. Clean separation. Python team owns the model; Java team owns the integration.

Best for: large models, GPU inference, frequent retraining
⚙️

Pattern 2: In-Process via ONNX

Train in Python, export to ONNX, load with ONNX Runtime for Java. Inference happens inside the JVM — no network hop, no latency.

Best for: low-latency scoring, edge cases, high-throughput
☕

Pattern 3: Java-Native ML

Use Tribuo, Weka, or DL4J — train and serve entirely in Java. No Python, no polyglot stack. Full JVM control.

Best for: simple models, regulated environments, Java-only shops

Spring Boot Calling an ML Service

@Service public class FraudDetectionService { private final WebClient mlClient; @Autowired public FraudDetectionService(WebClient.Builder builder) { this.mlClient = builder.baseUrl("http://ml-service:8000").build(); } public FraudScore score(Transaction tx) { // 1. Feature engineering — in Java, where the business logic lives TransactionFeatures features = FeatureEngineer.extract(tx); // 2. Call ML model over HTTP — non-blocking with WebClient return mlClient.post() .uri("/predict/fraud") .bodyValue(features) .retrieve() .bodyToMono(FraudScore.class) .block(Duration.ofMillis(50)); // 50ms SLA } } // Feature engineering happens HERE — in Java — where domain knowledge lives public class FeatureEngineer { public static TransactionFeatures extract(Transaction tx) { return new TransactionFeatures( tx.getAmount(), tx.getHourOfDay(), tx.getMerchantCategory(), accountHistory.getVelocity30d(tx.getAccountId()), geoService.getRiskScore(tx.getLocation()) ); } }
Key insight: Feature engineering stays in Java — that's where your domain knowledge, business rules, and data access live. The ML model only sees clean, structured features.
Pattern 2 in Action

ONNX Runtime Inside the JVM

// Maven dependency <dependency> <groupId>com.microsoft.onnxruntime</groupId> <artifactId>onnxruntime</artifactId> <version>1.17.0</version> </dependency> // Load model once at startup @Bean OrtSession riskModel() throws OrtException { OrtEnvironment env = OrtEnvironment.getEnvironment(); return env.createSession("models/risk_v3.onnx"); } // Inference — pure Java, no HTTP, sub-millisecond public float predictRisk(float[] features) { OnnxTensor input = OnnxTensor .createTensor(env, new float[][]{features}); OrtSession.Result result = session.run( Map.of("input", input)); return ((float[][]) result.get(0) .getValue())[0][0]; }

Why ONNX?

Train in scikit-learn, XGBoost, or PyTorch. Export once. Run everywhere — including inside your Spring Boot app, no Python runtime needed.

Performance

Sub-millisecond inference. No network overhead. Ideal for high-frequency scoring: 10,000+ transactions/second on a standard JVM.

Model Lifecycle

Retrain in Python on schedule. Swap the .onnx file. The Java service reloads seamlessly — zero downtime, zero code changes.

Serving Models

Exposing ML Models as REST APIs

# Python FastAPI — the ML model server from fastapi import FastAPI import joblib, numpy as np app = FastAPI() model = joblib.load("fraud_model_v3.pkl") @app.post("/predict/fraud") async def predict(features: TransactionFeatures): X = np.array([[ features.amount, features.hour_of_day, features.merchant_risk, features.velocity_30d, features.geo_risk ]]) prob = model.predict_proba(X)[0][1] return { "fraud_probability": float(prob), "is_fraud": prob > 0.85, "model_version": "v3.2.1" }

Why FastAPI?

Auto-generated OpenAPI schema. Java's RestTemplate or WebClient generates a typed client automatically. Contract-first integration.

Versioning Strategy

Version the model URL (/v3/predict). Java consumers pin to a version. Retrain without breaking existing Java callers.

Health + Observability

Expose /health and /metrics. Spring Actuator monitors it like any other downstream dependency. Track latency and drift together.

End to End

ML Pipeline Embedded in a Java Microservice

1

Data Ingestion — Kafka Consumer (Java)

Spring Kafka listener consumes transaction events. Raw events stored in PostgreSQL. Feature store (Redis) populated with rolling aggregates (velocity, averages).

2

Feature Engineering — Spring Service (Java)

Business-logic-heavy transformation: normalize amounts by account tier, compute time-of-day bins, enrich with merchant category risk from Java lookup tables.

3

Model Inference — ONNX Runtime (in-JVM)

Feature vector passed to ONNX session. Random Forest / XGBoost model returns probability score. Sub-millisecond. No network call. Thread-safe session pool.

4

Decision Logic — Spring Service (Java)

Score thresholding, confidence bands, ensemble voting. Business rules and ML scores combined — Java stays the decision authority. Full audit trail.

5

Action + Monitoring — Spring Actuator + Micrometer

Block / allow / review decisions. ML prediction accuracy tracked via Micrometer. Drift alerts trigger model retraining pipeline in Python. Prometheus + Grafana visualize it all.

Example 01 · Spring AI

Spring AI — The Missing Bridge

🔌

What is Spring AI?

Spring Framework's official AI integration library. Adds a unified abstraction over LLMs — the same way Spring Data abstracts databases. One API, any provider.

spring.io/projects/spring-ai
🔄

Provider Portability

Swap the Maven starter and one property — your Java code never changes. OpenAI → Claude → Ollama (local) → Azure OpenAI. Pick the right model for the right job.

Zero code change per provider switch
🎯

Structured Output

Call .entity(MyRecord.class) — Spring AI reflects on your Java record, builds a JSON schema, instructs the LLM, and deserialises the response automatically.

LLM → Java record in one line
✍️

Prompt Templates

Parameterised prompts with .text("...{param}...").param(k, v) — no string concatenation, no injection risk, clean separation of prompt logic from data.

🧠

Advisors & RAG

Built-in Retrieval Augmented Generation with vector stores (Postgres pgvector, Redis, Pinecone). Answer questions over your own documents with a few lines of Java.

🔧

Function Calling

Expose Java methods as LLM tools. The model decides when to call them. LLM orchestrates your existing Spring services — no agent framework needed.

// Step 1 — pom.xml: add ONE starter <dependency> <groupId>org.springframework.ai</groupId> <artifactId>spring-ai-openai-spring-boot-starter</artifactId> </dependency> // Step 2 — AiConfig.java: configure the ChatClient bean @Bean ChatClient chatClient(ChatClient.Builder builder) { return builder .defaultSystem("You are a senior fraud analyst...") .build(); } // Step 3 — Service: prompt + structured output public FraudExplanation explain(FraudAlert alert) { return chatClient.prompt() .user(u -> u .text("Analyze TX {txId}: amount {amount}...") .param("txId", alert.transactionId()) .param("amount", alert.amount())) .call() .entity(FraudExplanation.class); // LLM → Java record }
// FraudExplanation.java — Spring AI reflects on this public record FraudExplanation( String summary, // one-sentence verdict List<String> riskFactors, // exactly 3 factors String recommendedAction, // BLOCK | REVIEW | ALLOW String customerMessage, // plain-English String analystNote, // technical detail int urgencyScore // 1–10 ) {} // Example LLM response (auto-mapped): { "summary": "3 AM card-not-present FUEL exceeds normal patterns", "riskFactors": ["3 AM hour", "geo mismatch", "high velocity"], "recommendedAction": "BLOCK", "customerMessage": "We placed a hold for your security...", "analystNote": "92% prob — matches card-testing pattern", "urgencyScore": 9 }

Summary

5 Things to Remember

1. Java is not the problem

30 years of battle-tested code, domain knowledge, and business logic cannot be replaced. It must be extended. Java is your foundation, not your limitation.

2. Three integration patterns work

Model-as-a-service (REST), ONNX in-JVM, or Java-native ML. Each fits different latency, privacy, and operational requirements. Pick the right one per use case.

3. Feature engineering stays in Java

Your domain logic, business rules, and data access are in Java — that's where features should be built. The ML model should only see clean, engineered inputs.

4. Start with one production problem

Don't build a platform. Don't rewrite. Find one real problem — fraud, classification, anomaly detection — solve it end-to-end, and prove value before scaling.

5. Your Java skills are an unfair advantage

Most ML engineers don't know how to operate production systems. You do. The Java engineer who learns ML integration is 10× more valuable than either alone.
